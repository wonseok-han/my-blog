# 에이전트 워크플로우, 이론은 알겠고 실전에서는 어떻게 쓸까?

> **이 글의 자리**
> 이 글은 [에이전트 워크플로우와 개발자의 중심 잡기](/posts/21-에이전트-워크플로우와-개발자의-중심-잡기)의 실습편이다. 이론편의 두 축인 **정보**(무엇을 보여줄까)와 **판정**(무엇을 완료로 볼까)을 설정과 코드로 옮긴다.

Claude Code와 Codex 예시를 나란히 살펴본다.

## 1. 전체 구성: 컨텍스트·하네스·루프·에이전틱·그래프 실습

| 실습 영역 | 도구 중립 원칙 | Claude Code | Codex |
|---|---|---|---|
| **컨텍스트** — 항상 로드 | 코드를 읽어 알 수 없는 것만, 짧게 | `CLAUDE.md` (200줄 목표) | `AGENTS.md` (`project_doc_fallback_filenames`로 대체 파일명 지정 가능) |
| **컨텍스트** — 범위 지정 | 필요한 경로에서만 로드 | `.claude/rules/` + `paths:` | 하위 디렉터리별 `AGENTS.md` 계층 |
| **컨텍스트** — 온디맨드 | 절차와 도구는 필요할 때만 | Skills, MCP 선택, tool search | Skills, MCP |
| **하네스** — 사전 차단 | 실행 가능한 경계로 막는다 | `permissions.deny`, `PreToolUse` | `sandbox_mode`, `writable_roots`, `PreToolUse` |
| **하네스** — 사후 교정 | 실행 결과를 검사한다 | `PostToolUse`, 테스트·린터 | `PostToolUse`, 테스트·린터 |
| **루프** | 검사 결과를 다음 실행에 연결한다 | `Stop`, `maxTurns` | `Stop`, `/goal` |
| **에이전틱** — 감독 | 사람이 확인할 시점을 정한다 | 퍼미션 모드 | `approval_policy` (`untrusted` / `on-request` / `never` / `granular`) |
| **에이전틱** — 위임 | 독립 작업의 컨텍스트를 분리한다 | 서브에이전트 | 서브에이전트 |
| **그래프** | 조건에 따라 다음 단계와 복귀 지점을 고른다 | LangGraph 같은 외부 런타임 또는 직접 구현 | LangGraph 같은 외부 런타임 또는 직접 구현 |

두 제품은 같은 원칙을 서로 다른 설정으로 구현한다. 정보가 부족하면 규칙 파일이나 Skills를, 판정이 모호하면 테스트·훅·CI를 보강한다. 위험한 행동은 프롬프트가 아니라 권한과 샌드박스로 막는다.[^ccmemory][^codex]

> 아래 예시의 설정 형식은 2026년 8월 기준 공식 문서를 따랐다. 도구는 빠르게 바뀌므로 적용 전 문서 확인을 권한다.[^ccmemory][^cchooks][^ccsubagents][^codex]

## 2. 컨텍스트 엔지니어링 실습: 규칙 파일·Skills·MCP로 입력 구성하기

### 2.1 `CLAUDE.md`와 `AGENTS.md`: 항상 로드되는 정보 줄이기

`CLAUDE.md`와 `AGENTS.md`는 모델에 주입되는 지침이지 강제 설정이 아니다.

> "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but **there's no guarantee of strict compliance**."[^ccmemory]

강제 차단은 훅이나 권한 설정으로 내려보내야 한다. Claude Code는 `CLAUDE.md`를 200줄 아래로 유지하도록 권하며, `@path`로 파일을 나눠도 모두 로드되므로 토큰은 줄지 않는다.[^ccmemory]

컨텍스트를 줄이는 방법은 세 가지다.

**(a) 경로 스코프 규칙** — `.claude/rules/`에 `paths:` frontmatter를 쓰면 **매칭되는 파일을 읽을 때만** 로드된다. 이게 진짜 just-in-time이다.

```markdown
<!-- .claude/rules/api.md -->
---
paths: # 이 규칙을 불러올 파일 범위
  - "src/api/**/*.{ts,tsx}" # API의 TypeScript 파일에만 적용
---

# API 규칙

- 모든 엔드포인트는 입력 검증을 포함한다
- 에러 응답은 `src/api/errors.ts`의 표준 포맷을 쓴다
```

`paths`가 없는 규칙은 매 세션 로드된다. 전역 규칙만 `CLAUDE.md`에 남기고 나머지는 경로로 제한한다.

Codex의 계층 규칙은 로딩 시점이 다르다. 작업을 시작할 때 프로젝트 루트부터 현재 작업 디렉터리까지 내려오며 `AGENTS.md`를 합친다. 저장소 공통 규칙과 모듈별 규칙은 다음처럼 나눌 수 있다.

```text
repo/
├── AGENTS.md                    # 저장소 공통 규칙
└── services/
    ├── payments/
    │   ├── AGENTS.md            # 결제 모듈 규칙
    │   └── src/
    └── search/
        └── AGENTS.md            # 검색 모듈 규칙
```

루트에는 공통 규칙을 두고:

```markdown
<!-- AGENTS.md -->
# 저장소 공통 규칙

- 공개 API를 바꾸면 마이그레이션 문서를 갱신한다
- 커밋 전 `pnpm test`를 실행한다
```

결제 모듈에는 더 좁은 규칙을 둘 수 있다.

```markdown
<!-- services/payments/AGENTS.md -->
# 결제 모듈 규칙

- 통합 테스트는 `make test-payments`로 실행한다
- 결제 요청과 응답에 시크릿을 기록하지 않는다
```

결제 모듈에서 시작하면 두 파일이 루트부터 합쳐지고 하위 규칙이 우선한다. Claude Code의 `paths:`와 달리 시작 시 현재 작업 디렉터리까지만 읽는다.[^codex]

**(b) Skills** — 규칙(`rules/`)은 매 세션 또는 매칭 시 로드되지만, Skills는 **호출하거나 관련 있다고 판단될 때 본문이 로드된다.** Claude Code와 Codex 모두 이 방식을 지원한다. 다단계 절차나 특정 작업에서만 필요한 참고 자료는 Skills로 분리한다.[^codex]

**(c) HTML 주석** — Claude Code에서는 블록 레벨 HTML 주석이 컨텍스트에 주입되기 전에 제거된다. 유지보수 노트를 **토큰 0**으로 남길 수 있다(코덱스에는 해당 기능이 없다).

```markdown
<!-- 2026-05: 빌드 스크립트 변경 시 이 섹션 갱신 (담당: 인프라팀) -->
## 빌드
- `pnpm build` (npm 아님)
```

규칙은 구체적으로 쓴다.[^ccmemory]

| ❌ | ✅ |
|---|---|
| "코드를 깔끔하게 포맷하세요" | "2-space 인덴트를 쓴다" |
| "변경 사항을 테스트하세요" | "커밋 전에 `npm test`를 돌린다" |
| "파일을 정리하세요" | "API 핸들러는 `src/api/handlers/`에 둔다" |

중복·충돌·낡은 규칙을 지우고, 규칙 파일에는 **코드를 읽어서 알 수 없는 것**만 남긴다.

### 2.2 Skills와 MCP: 절차와 도구를 필요할 때 불러오기

도구가 많아지면 선택 성능과 입력 토큰에 영향을 줄 수 있다. 다만 몇 개부터 문제라는 공통 기준은 없다.[^longfunceval][^mcpgauge]

다음은 온디맨드 로딩이 적용된 Claude Code 세션에서 `/context`를 확인한 한 사례다.

```text
Context Usage                                  247.1k/1m tokens (25%)
  System prompt          5.4k  (0.5%)
  System tools            10k  (1.0%)
  Memory files            351  (0.0%)
  Skills                 2.5k  (0.3%)
  Messages             228.9k  (22.9%)

MCP tools · /mcp (loaded on-demand)
└ 24 tools · 0 tokens          ← 24개인데 0 토큰

Skills · /skills
└ 23 skills · 2.5k tokens      ← 23개가 설명만 2.5k
```

이 세션에서는 MCP 도구 정의가 온디맨드로 처리됐고, Skills는 이름과 설명만 먼저 들어갔다. Codex Skills도 선택된 뒤 전체 `SKILL.md`를 읽는다. 숫자는 환경마다 다르므로 절감률로 일반화할 수 없다.[^codex]

필요한 도구만 켜고, 가능하면 검색이나 온디맨드 로딩으로 고른다.[^ragmcp][^toolsearch]

## 3. 하네스 엔지니어링 실습: 권한·샌드박스·`PreToolUse`로 실행 제한하기

Claude Code에서는 `permissions.deny`로 단순한 금지 규칙을, `PreToolUse`로 조건이 있는 차단을 구현한다.[^ccmemory]

아래 JSON 설정은 설명용 주석을 넣기 위해 JSONC로 표기했다. 사용하는 도구가 주석을 지원하지 않으면 주석을 제거하고 저장한다.

`.claude/settings.json`:

```jsonc
{
  "permissions": { // 도구 실행 권한 설정
    "deny": [ // 조건에 맞으면 항상 차단
      "Read(./.env)", // .env 읽기 차단
      "Read(./secrets/**)", // secrets 하위 파일 읽기 차단
      "Bash(git push:*)" // git push 명령 차단
    ]
  }
}
```

규칙 파일의 지시와 달리 이 설정은 클라이언트가 집행한다.

조건이 복잡하면 `PreToolUse` 훅을 쓴다. **exit code 2가 차단**이다.

`.claude/settings.json`:

```jsonc
{
  "hooks": { // 훅 등록
    "PreToolUse": [ // 도구 실행 직전에 호출
      {
        "matcher": "Bash", // Bash 도구에만 적용
        "hooks": [ // 조건이 맞을 때 실행할 훅
          {
            "type": "command", // 외부 명령 실행
            "command": "${CLAUDE_PROJECT_DIR}/.agent-hooks/guard-bash.sh", // 실행할 스크립트
            "timeout": 10 // 최대 실행 시간(초)
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .agent-hooks/guard-bash.sh — Claude Code와 Codex가 함께 사용
input=$(cat)
cmd=$(jq -r '.tool_input.command' <<<"$input")

if grep -qE 'rm -rf|:> *\.env' <<<"$cmd"; then
  echo "파괴적 명령 차단: $cmd" >&2
  exit 2          # 2 = 강제 차단, stderr가 이유로 전달된다
fi
exit 0
```

Codex에서는 같은 스크립트를 `.codex/hooks.json`에 등록한다. `.codex/config.toml`은 필요하지 않다.

`.codex/hooks.json`:

```jsonc
{
  "hooks": { // 훅 등록
    "PreToolUse": [ // 도구 실행 직전에 호출
      {
        "matcher": "^Bash$", // Bash 도구와 정확히 일치
        "hooks": [ // 조건이 맞을 때 실행할 훅
          {
            "type": "command", // 외부 명령 실행
            "command": "/bin/bash \"$(git rev-parse --show-toplevel)/.agent-hooks/guard-bash.sh\"", // 저장소 루트의 스크립트 실행
            "timeout": 10, // 최대 실행 시간(초)
            "statusMessage": "Checking shell command" // 실행 중 표시할 메시지
          }
        ]
      }
    ]
  }
}
```

Codex도 JSON 입력과 exit code 2를 사용한다. 프로젝트 훅은 추가하거나 바꾼 뒤 `/hooks`에서 신뢰해야 실행된다. `matcher`에는 `Bash`, `Edit|Write`, MCP 도구 패턴 등을 지정할 수 있다.[^codex]

샌드박스는 훅의 선행 조건이 아니라 별도의 실행 경계다. 훅은 모든 실행 경로를 포괄하지 않으므로 샌드박스를 대체하지 않는다.[^codex]

## 4. 루프 엔지니어링 실습: `PostToolUse`·`Stop`·`/goal`로 검증 반복하기

훅은 작업 흐름의 특정 시점에 스크립트를 실행하는 장치다. 여기서 도구는 `Bash`, `Edit`·`Write`, `apply_patch`, MCP처럼 에이전트가 실제 행동에 사용하는 기능을 뜻한다.[^codex]

- **PostToolUse**: `matcher`에 지정한 도구가 끝난 직후 실행한다.
- **Stop**: 에이전트가 현재 작업을 끝내려 할 때 실행한다.[^codex]

*"테스트 코드를 작성해줘*"라는 요청은 다음처럼 진행될 수 있다.

```text
apply_patch로 테스트 파일 작성
  → PostToolUse 실행 ①
  → apply_patch로 테스트 보완
  → PostToolUse 실행 ②
  → 작업 완료 시도
  → Stop 실행
```

`PostToolUse`는 코드 한 줄마다가 아니라 도구 호출마다 실행된다. 빠른 부분 린트는 `PostToolUse`에, 전체 테스트처럼 무거운 검사는 `Stop`에 두면 불필요한 반복을 줄일 수 있다. 아래의 `Edit|Write`는 파일 수정 도구만 대상으로 삼는다.

```jsonc
{
  "hooks": { // 훅 등록
    "PostToolUse": [ // 도구 실행이 끝난 직후 호출
      {
        "matcher": "Edit|Write", // 파일 수정 도구에만 적용
        "hooks": [ // 조건이 맞을 때 실행할 훅
          {
            "type": "command", // 외부 명령 실행
            "command": "${CLAUDE_PROJECT_DIR}/.agent-hooks/lint-changed.sh" // 변경 파일 검사
          }
        ]
      }
    ]
  }
}
```

여기에 이론편의 [3.2절 사람이 정해야 하는 것은 남긴다](/posts/21-에이전트-워크플로우와-개발자의-중심-잡기#32-사람이-정해야-하는-것은-남긴다)에서 말한 **"무엇이 완료인가**"까지 `Stop` 훅으로 코드화할 수 있다.

```jsonc
{
  "hooks": { // 훅 등록
    "Stop": [ // 에이전트가 작업을 끝내기 직전에 호출
      {
        "hooks": [ // Stop 시 실행할 훅
          {
            "type": "command", // 외부 명령 실행
            "command": "${CLAUDE_PROJECT_DIR}/.agent-hooks/definition-of-done.sh", // 완료 조건 검사
            "timeout": 300 // 최대 실행 시간(초)
          }
        ]
      }
    ]
  }
}
```

```bash
#!/bin/bash
# .agent-hooks/definition-of-done.sh — Claude Code와 Codex가 함께 사용
# 완료 기준: 타입체크 통과 + 테스트 통과. 실패하면 턴을 끝내지 못한다.

fail=""
typecheck_log=$(mktemp)
test_log=$(mktemp)
trap 'rm -f "$typecheck_log" "$test_log"' EXIT

pnpm typecheck >"$typecheck_log" 2>&1 || fail="타입체크 실패: $(tail -3 "$typecheck_log")"
pnpm test >"$test_log" 2>&1 || fail="${fail:+$fail / }테스트 실패: $(grep -E '✕|FAIL' "$test_log" | head -3)"

if [ -n "$fail" ]; then
  jq -n --arg r "$fail" '{decision: "block", reason: $r}'
  exit 0
fi
jq -n '{}'
exit 0
```

Codex에서는 앞의 `.codex/hooks.json`에 다음 두 항목을 `PreToolUse`와 나란히 추가한다.

```jsonc
"PostToolUse": [
  {
    "matcher": "Edit|Write", // 파일 수정 도구에만 적용
    "hooks": [ // 도구 실행 뒤 호출할 훅
      {
        "type": "command", // 외부 명령 실행
        "command": "/bin/bash \"$(git rev-parse --show-toplevel)/.agent-hooks/lint-changed.sh\"" // 변경 파일 검사
      }
    ]
  }
],
"Stop": [
  {
    "hooks": [ // 작업 종료 전에 호출할 훅
      {
        "type": "command", // 외부 명령 실행
        "command": "/bin/bash \"$(git rev-parse --show-toplevel)/.agent-hooks/definition-of-done.sh\"", // 완료 조건 검사
        "timeout": 300 // 최대 실행 시간(초)
      }
    ]
  }
]
```

`PostToolUse`는 이미 생긴 부작용을 취소하지 못한다. `Stop`이 `decision: "block"`과 실패 이유를 반환하면 Codex는 작업을 이어간다. 성공 시 `{}`를 출력한다.[^codex]

검사 결과는 로그 전문 대신 실패 원인만 짧게 반환한다.[^harnessbench][^contextrot]

여러 턴에 걸친 작업은 `/goal`에 범위, 검증 명령, 정지 조건을 적어 둘 수 있다. CI도 같은 완료 기준을 PR 단계에서 집행한다.[^codex]

## 5. 에이전틱 엔지니어링 실습: 퍼미션 모드와 서브에이전트 설계하기

### 5.1 퍼미션 모드와 승인 정책: 사람이 확인할 시점 정하기

Claude Code에서는 퍼미션 모드로 사람이 확인할 시점을 정한다. 아래 표는 `Shift+Tab`으로 순환하는 목록이 아니라 **지원하는 전체 모드**다.[^ccpermmodes]

| 모드 (설정값) | 표시 이름 | 묻지 않고 실행되는 것 |
|---|---|---|
| `default` | Manual | 읽기 |
| `acceptEdits` | Edit automatically | 읽기 + 작업 디렉터리 내 파일 편집과 일반적인 파일 명령 |
| `plan` | Plan | 코드 탐색과 계획 작성 (소스 편집 차단) |
| `auto` | Auto | 별도 분류기가 허용한 행동 |
| `dontAsk` | Don't ask | 미리 승인된 것만 (그 외 자동 거부) |
| `bypassPermissions` | Bypass permissions | 퍼미션 계층을 우회 |

CLI의 `Shift+Tab` 기본 사이클은 `default` → `acceptEdits` → `plan`이다.

- `auto`는 지원 조건을 만족할 때 사이클에 추가된다.
- `bypassPermissions`는 실행 옵션이나 설정으로 먼저 허용해야 사이클에 나타난다.
- `dontAsk`는 `Shift+Tab` 사이클에 나타나지 않는다. `claude --permission-mode dontAsk`로 지정한다.
- Desktop과 VS Code에서는 `Shift+Tab`이 아니라 모드 선택기를 사용한다.

`auto`는 별도 분류기 모델이 행동을 심사한다. 대화에서 말한 경계는 컴팩션 뒤 사라질 수 있으므로 확실한 금지는 `deny`로 둔다. 넓은 allow 규칙은 auto 진입 시 빠지고, 서브에이전트의 `permissionMode`도 무시된다. 분류기 호출은 토큰과 왕복 시간을 추가한다.[^ccpermmodes]

- 되돌리기 어려운 작업은 `plan`에서 검토한 뒤 실행한다.
- 결제나 배포 경로는 `PreToolUse`에서 별도로 막는다.

Codex는 승인 여부를 `approval_policy`, 실행 범위를 `sandbox_mode`로 나눈다. 서브에이전트도 현재 작업의 퍼미션 모드와 샌드박스 정책을 적용받는다.[^codex]

### 5.2 서브에이전트: 탐색과 리뷰 컨텍스트 분리하기

서브에이전트는 검색 결과나 로그를 별도 컨텍스트에서 처리하고 요약만 반환할 때 유용하다.[^ccsubagents][^codex]

```markdown
<!-- .claude/agents/log-digger.md -->
---
name: log-digger # 에이전트를 식별할 이름
description: 실패한 CI 로그에서 원인 후보만 추려서 보고할 때 사용 # 언제 사용할지 설명
tools: Read, Grep, Glob, Bash # 사용할 수 있는 도구
model: haiku # 사용할 모델
maxTurns: 12 # 최대 작업 턴 수
---

CI 로그를 조사한다. 로그 원문을 그대로 옮기지 말고,
실패한 테스트 이름과 근본 원인 후보를 최대 5줄로 요약해 보고한다.
```

이 예시는 `tools`로 쓰기를 막고, 작은 모델과 `maxTurns`로 비용을 제한한다. 위임 여부는 다음 세 질문으로 판단한다.

| 질문 | 이득이 있는 경우 | 손실인 경우 |
|---|---|---|
| **① 압축비** — 읽을 양 ÷ 돌려줄 양 | 파일 20개를 읽고 발견 5줄을 반환 (크다) | 읽은 내용을 거의 그대로 요약 없이 반환 (1에 가깝다) |
| **② 관점 분리** — 깨끗한 컨텍스트가 결과를 바꾸는가 | **리뷰·검증** — 메인의 "내가 왜 이렇게 썼는지"라는 정당화를 물려받지 않는 게 장점 | 단순 조회 — 누가 읽어도 같은 답 |
| **③ 재참조** — 원문을 나중에 또 볼 필요가 있는가 | 없다 (발견만 필요) | 있다 — 요약만 남으면 메인이 결국 다시 읽는다 |

Codex는 `default`, `worker`, `explorer` 서브에이전트를 기본 제공한다. 별도 설정 없이 프롬프트로 위임할 수 있고, 역할별 설정이 필요할 때만 커스텀 에이전트를 만든다.[^codex]

```toml
# .codex/agents/architecture-reviewer.toml
name = "architecture_reviewer" # 에이전트를 식별할 이름
description = "변경된 코드가 프로젝트의 계층 규칙과 에러 처리 관례를 지키는지 검토한다." # 언제 사용할지 설명
model_reasoning_effort = "high" # 추론 수준
sandbox_mode = "read-only" # 파일 수정을 막고 읽기만 허용

# 에이전트가 따라야 할 작업 지침
developer_instructions = """
변경분을 git diff로 확인하고 아래 기준으로만 검토한다.

1. 도메인 레이어가 인프라 레이어를 직접 import하지 않는가
2. 에러가 src/api/errors.ts 표준 포맷을 쓰는가
3. 공개 API 변경에 마이그레이션 노트가 있는가

각 발견을 `파일:줄 — 문제 — 근거` 한 줄로 보고한다.
코드 원문을 옮겨 적지 말고, 발견이 없으면 "없음"만 답한다.
"""
```

위 파일은 커스텀 에이전트의 최소 예시다. `name`, `description`, `developer_instructions`는 필수고, 나머지는 선택이다. `model`, `model_reasoning_effort`, `sandbox_mode`, `mcp_servers`, `skills.config` 등 일반 `config.toml` 설정을 추가할 수 있다. 생략한 값은 부모 작업의 설정을 상속한다.[^codex]

동시 실행 수와 기본 모델·추론 수준은 `.codex/config.toml`의 `[agents]`에서 설정한다.

```toml
# .codex/config.toml
[agents] # 서브에이전트 공통 설정
max_concurrent_threads_per_session = 4 # 동시에 실행할 수 있는 최대 서브에이전트 수
default_subagent_reasoning_effort = "medium" # 별도 지정이 없을 때 사용할 추론 수준
```

위임의 이득은 반환 형식과 권한을 좁힐 때 생긴다.[^codex]

반대로 다음과 같은 위임은 격리의 이점을 살리지 못한다.

- **압축 없는 위임** — "이 파일 읽고 알려줘" 수준. 메인이 직접 읽는 게 싸다.
- **인수인계가 긴 위임** — 파일 소유권과 반환 형식을 좁힌다.
- **병렬 팬아웃 남발** — 같은 코드베이스를 반복해서 읽으면 토큰과 조정 비용이 늘어난다.[^cognition][^multiagent]

## 6. 그래프 엔지니어링 실습: LangGraph로 조건 분기와 부분 재시도 구성하기

서브에이전트 하나에 독립 작업을 맡기는 것만으로 충분하다면 그래프를 추가할 이유는 없다. 그래프가 필요한지는 에이전트 수가 아니라 **제어 흐름**으로 판단한다. 다음과 같은 요구가 반복해서 나타날 때 검토할 수 있다.

- 실패 원인에 따라 정보 수집이나 구현처럼 서로 다른 단계로 돌아가야 한다.
- 외부 변경이나 고위험 작업 전에 인간 승인 단계가 필요하다.
- 중단된 작업을 처음부터 다시 하지 않고 특정 상태에서 재개해야 한다.
- 각 단계의 재시도 횟수와 실행 한도를 따로 관리해야 한다.

LangGraph는 이런 흐름을 코드로 표현하는 도구 중 하나다. 아래 예시는 검토 결과에 따라 구현으로 돌아가거나, 인간 승인으로 보내거나, 종료하는 조건부 경로를 보여준다.[^graphframeworks]

```python
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    draft: str
    errors: list[str]
    needs_approval: bool

def route(state: State) -> Literal["write", "approval", "__end__"]:
    if state["errors"]:
        return "write"
    if state["needs_approval"]:
        return "approval"
    return END

g = StateGraph(State)
g.add_node("write", write_fn)
g.add_node("review", review_fn)
g.add_node("approval", approval_fn)
g.add_edge(START, "write")
g.add_edge("write", "review")
g.add_conditional_edges("review", route)
g.add_edge("approval", END)
app = g.compile()
```

이 예시에서 그래프는 여러 에이전트를 전제로 하지 않는다. `write_fn`, `review_fn`, `approval_fn`은 결정론적 코드나 모델 호출, 도구 실행, 인간 검토 중 무엇으로도 구현할 수 있다. 여러 에이전트를 노드로 두는 것은 한 가지 선택일 뿐이다.

그래프를 도입해도 각 단계에 어떤 정보를 주고 무엇을 성공으로 판정할지는 여전히 앞 절의 원칙으로 정한다. 분기와 부분 재시도는 불필요한 전체 재실행을 줄일 수 있지만, 상태 저장·추적·복구 경로를 관리하는 비용이 추가된다. 여러 에이전트까지 병렬로 연결하면 모델 호출과 조정 비용도 더 커진다. 따라서 단일 루프로 표현하기 어려운 경로가 실제로 생겼을 때 도입하는 편이 낫다.

## 7. 요구사항을 설정으로 옮기는 체크리스트

| 하려던 것 | ❌ 흔한 방식 | ✅ 이렇게 |
|---|---|---|
| 편집 직후 린트 피드백 | 규칙 파일에 "수정 후 린트하세요" | `PostToolUse`(Edit\|Write) 훅 |
| 커밋 전 린트 강제 | 규칙 파일에 "커밋 전 린트하세요" | pre-commit hook 또는 CI |
| 시크릿 보호 | 규칙 파일에 "`.env`는 읽지 마세요" | Claude Code: `permissions.deny` / Codex: 파일 권한·`PreToolUse` |
| 완료 기준 전달 | 프롬프트에 "테스트 통과하면 끝" | `Stop` 훅에서 테스트 실패 시 `decision: "block"` |
| 규칙 파일 다이어트 | 파일만 쪼개고 전부 로드 | Claude Code: `paths:` / Codex: 작업 위치별 `AGENTS.md` 계층 |
| 대규모 코드 탐색 | 메인 세션에 검색 결과를 모두 남기기 | 서브에이전트가 탐색하고 근거와 결론만 반환 |
| 코드 리뷰 | 구현 과정만 다시 훑기 | 검토 기준을 명시하고 별도 리뷰 단계에서 확인 |
| 도구 늘리기 | 여러 MCP 서버를 상시 활성화 | 작업에 필요한 것만, 나머지는 온디맨드 |
| 아키텍처 규칙 | `CLAUDE.md`에 300줄 아키텍처 설명 | 검증 가능한 것은 린트 규칙으로, 나머지는 경로 스코프 규칙으로 |
| 유지보수 메모 | 규칙 파일에 주석 문장으로 | 블록 HTML 주석(`<!-- -->`) — 토큰 0(Claude Code만 해당, 코덱스는 미지원) |
| 특정 작업 금지 | 대화로 "푸시하지 마" | Claude Code: `deny` / Codex: 샌드박스·`PreToolUse` |
| 서브에이전트 권한 축소 | 작업 설명에 "읽기만 하라" | Claude Code: `tools`·`disallowedTools` / Codex: `sandbox_mode = "read-only"` |

## 8. 가장 작은 설정부터 적용하는 순서

지금까지의 설정을 한꺼번에 적용하려 하면 오히려 복잡도만 늘어난다. 본문의 작은 단위에서 큰 단위로 올라가며 다음 순서로 적용하는 편이 낫다.

1. **측정한다.** 세션 시작 시점의 컨텍스트 점유율을 기록한다. 이 숫자가 앞으로의 기준선이다. *(Claude Code: `/context`)*
2. **규칙 파일을 깎는다.** 200줄 아래를 목표로, 코드를 읽어서 알 수 있는 건 다 지운다. `/doctor`의 크기 경고는 참고하되, 내용은 직접 검토한다.
3. **적용 범위를 좁힌다.** 특정 디렉터리에서만 필요한 규칙은 그 경로에 묶어 둔다. *(Claude Code: `.claude/rules/` + `paths:` / Codex: 하위 모듈별 `AGENTS.md` 계층)*
4. **도구를 줄인다.** 현재 작업에 필요하지 않은 MCP 서버를 끈다.
5. **실행 경계를 만든다.** "~해야 한다"로 시작하는 문장을 훑어서, 결정론적으로 차단 가능한 것을 권한·샌드박스·`PreToolUse`로 옮긴다.
6. **완료 기준을 루프로 만든다.** 타입체크·테스트를 걸고, 실패 원인을 짧고 충분하게 전달한다. *(`Stop` 훅, 또는 CI 필수 통과 게이트)*
7. **필요할 때만 위임한다.** 반환 결과가 원문보다 충분히 짧거나 별도 관점이 필요할 때 서브에이전트를 쓴다.
8. **분기와 복귀가 생길 때만 그래프로 간다.** 단일 루프로 표현할 수 있다면 그래프를 추가하지 않는다.
9. **다시 측정한다.** 설정을 추가하기 전보다 결과가 나아졌는지 확인하고, 차이가 없다면 제거한다.

Anthropic 자신의 원칙도 같은 방향이다 — *"가장 단순한 해법을 찾고, 필요할 때만 복잡도를 올려라"*, *"더 단순한 해법이 부족할 때만"*.[^simple]
